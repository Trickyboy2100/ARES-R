变体后缀

同一核心功能的不同末状态或实验版本增加 -01、-02 等两位后缀。基础业务表保留五位码；别名映射显式登记变体，禁止通过省略后缀猜测 Utility。

默认操作臂记录在参数 arm=right，版本、速度、Golden/Delivered 状态和算法模式均作为 metadata。未来左臂复用核心业务号时，新增明确变体及 arm 字段。

完整跨工位任务采用独立 Scheme 编号，例如 S-A0-B2-01，关联多个 F/P 功能及导航。避免用单个取或放编号隐藏底盘转场。

抓取功能与参数

共同流程

在指定工位静止 → 读取当前关节、TCP、工具与夹爪 → Epic匹配和新场景 → 检测坐标变换及任务偏置 → 预抓取规划 → 预开夹爪 → 接近目标 → 闭爪 → 延时回读和抓取验证 → 指定脱离/抬升 → 持稳结束。

新独立 Fetch 的末状态定义为 HOLD_CONFIRMED。原位抓放测试分支在持稳后继续下降、释放、退出和回center。提取独立 Fetch 时明确终止点，保留原先已验证的接近、闭合和抬升执行段。

自由空间复用现有 SceneAwareMotion/cuRobo；接触段沿用对应成功版本的动作和范围。每个新工位独立绑定目标、工具、物体、接触方向及退出通道。

典型Scheme

S-A0-B2-01 按顺序调用 AA0F0 → 交接/转场姿态 → 已绑定导航路线 → B2到站 → AB2P5 → 返回站。ROS对应 RA0F0 与 RB2P5，通过业务编排接导航。单个ScanPick/ScanPlace不隐含底盘移动。

同一个Fetch用于不同目的地时，Scheme显式选择兼容的handover profile。目标改变导致profile不匹配时，先生成对应持物姿态转换，再交给Place；底盘移动后重建场景。

连续五次和反向任务

连续放置任务每轮选择空泊位、预留、抓取、转场、放置、释放确认、提交占用；失败时保留实际持物状态和泊位预留状态。下一轮根据真实结果选择槽位。

从烘干箱取回天平调用对应 BxFn → 转场 → A0P0。抓取完成确认后更新源槽为空，目标放置完成后更新目标状态。任务编号、request_id、payload_session和slot reservation用于关联各步骤。

现有六槽占用表与这些状态的原子提交还需逐项核对实现。手册中的编排为扩展设计，当前不标记已交付。

并行边界

允许优先评估SDK/模型预加载、证据异步写盘、下一段参数准备。依赖真实末态的场景、目标和最终轨迹绑定保留在对应时点。底盘与持物机械臂同时运动属于另一个联合验收范围，已成功的串行任务继续作为基线。

从原生验证到 ROS 交付

实施顺序

  1. 从现场最新成功原生Demo选择执行器和有效参数。
  2. 在ART/WebUI确认业务末状态，例如独立Fetch在持物时结束、Place完成退出及规定的center。
  3. 固化输入输出、参数revision、工具/模型绑定和成功证据。
  4. ROS薄封装调用同一个canonical backend任务，提供反馈、取消、最终结果和重复请求处理。
  5. 完成模拟/回放后，做ROS客户端真实调用与跨机器通信验收。
  6. 打包源码、消息定义、launch/client、简短README、版本与哈希，记录Delivered。

原生完整成功直接作为业务实现基线。ROS适配新增的终止点、参数绑定和结果传播单独核对；保留所有真实成功记录。

接口形态

Utility保持既有 /ares_r/return_center、/ares_r/center_restore ABI。业务取放复用 /ares_r/run_block 及registry，传业务ID、参数版本、目标槽位与请求标识。A/R新编号先建立显式映射，交付时附旧ID兼容关系。

RunBlock现有定义及服务位于 release/ros1-business-blocks/ros/ares_r_manipulation_blocks/。旧P05/L03泛指烘干箱能力，六槽ID明确目标；迁移时绑定到具体槽或要求slot参数，不能默认覆盖到另一槽。

每次完整实机成功、有效参数变更、ROS完整联调或交付包生成后，更新对应条目。未完成实验只更新last_attempt，保留last_full_physical_success。重要阶段结束形成版本与Git提交。

维护者读取真实result/native/controller反馈后，更新catalog状态、参数SHA、证据路径与相应流程文档。构建器负责格式与链接一致性，实机结论由证据审阅产生。网页页头显示文档版本与证据日期，避免静态手册被理解为实时运行状态。
