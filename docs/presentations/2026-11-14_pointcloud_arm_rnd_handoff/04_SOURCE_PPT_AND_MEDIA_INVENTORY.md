## 3. 大PPT“最后很多页看似空白”的特殊处理

1. **必须先按源PPT本身slide序号检查**，不能只抓解析出的文字。大PPT从正式结论后有大量未写正文的幻灯片，它们可能含嵌入高质量图像、视频或画布组件。至少制作一个原始全页缩略图索引，逐页登记滑动截图、片段、备选草图和原始Media关系。
2. 推荐在可正常运行的本地环境 \`python-pptx\` 对整页shape统计、LibreOffice/PPT真正渲染；再用本目录 \`scripts/extract_pptx_slide_media.py\` 提取幻灯片相关\`ppt/media\`字节，保存slide→媒体文件→SHA清单。
3. 同一个屏幕截图只用一次，并以“完整实机画面 / 原始点云 / 结构分解 / 规划轨迹 / WebUI运行态 / 教程或示意”的状态分类。只在真正需要叙事对照时作裁切；不得裁掉否定结果、错误码、标注后制造“已成功”。
4. 同样扫描 \`周进度汇报学习-2-offline.zip\`、9/11和9/24周报原PPT（若本地有）里点云框拖拽/录屏素材，区分示意预览和真实执行。
5. 所有单个可用媒体重命名为稳定英文/数字路径，输出 \`media_manifest.csv\`：源ppt、原页、媒体zip条目、SHA256、分辨率、类别、证据等级、允许发布/仅内部使用、用途页码。

## 4. 上传与拆分策略（当前尚未执行）

**不要直接将263MB PPTX作为单个GitHub blob提交**，GitHub常规单文件上限为100MiB附近且仓库会膨胀。更好的方案是提交**精选原图/原始可编辑图件**而非重复嵌入的超大PPT。原参考PPT若用户坚持完整追溯，优先用Git LFS或独立许可的归档位置保存，并在此写可核验SHA。

如果用户确实要求把完整原版以普通Git保存为若干块，可在**本地**先做按字节约40MiB的分块（每块都不超过GitHub上限），生成 \`SHA256SUMS\`，加入只用于重组的 \`split_binary_pptx.sh\` 或Python脚本；必须事先评估项目仓库增长和敏感内容，**不允许把未经授权的真实现场私有媒体公开push**。当前GitHub连接器可写文本但当前容器不能读取上传的原始二进制，所以本次没有执行分片/上传，不能制造不存在的文件路径。

验收时至少应在远端检查每个part及SHA，取回重组后与原件的SHA完全一致；若改为拆分成多个可播放的子PPT，则需另行验证母版、关系、备注、媒体和页序，没有自动等价保证。
