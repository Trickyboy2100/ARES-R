# 从原生验证到 ROS 交付

## 实施顺序

1. 从现场最新成功原生Demo选择执行器和有效参数。
2. 在ART/WebUI确认业务末状态，例如独立Fetch在持物时结束、Place完成退出及规定的center。
3. 固化输入输出、参数revision、工具/模型绑定和成功证据。
4. ROS薄封装调用同一个canonical backend任务，提供反馈、取消、最终结果和重复请求处理。
5. 完成模拟/回放后，做ROS客户端真实调用与跨机器通信验收。
6. 打包源码、消息定义、launch/client、简短README、版本与哈希，记录Delivered。

原生完整成功直接作为业务实现基线。ROS适配新增的终止点、参数绑定和结果传播单独核对；保留所有真实成功记录。

## 接口形态

Utility保持既有 `/ares_r/return_center`、`/ares_r/center_restore` ABI。业务取放复用 `/ares_r/run_block` 及registry，传业务ID、参数版本、目标槽位与请求标识。A/R新编号先建立显式映射，交付时附旧ID兼容关系。

`RunBlock`现有定义及服务位于 `release/ros1-business-blocks/ros/ares_r_manipulation_blocks/`。旧P05/L03泛指烘干箱能力，六槽ID明确目标；迁移时绑定到具体槽或要求slot参数，不能默认覆盖到另一槽。

## 交付状态清单

| 原生证据 | ROS状态 | 可以声明的范围 |
|---|---|---|
| 完整成功且参数清楚 | 待封装 | 原生功能已验证，可优先适配 |
| 完整成功但当前参数更新 | 已有adapter | 历史成功成立，当前参数差异待绑定 |
| 原位抓放成功 | 独立HOLD未联调 | 抓取执行段可复用，独立出口待确认 |
| 仅规划 | 消息与服务已定义 | 软件接口候选、规划记录 |
| 完整原生+ROS调用+交付包 | Delivered | 明确版本及范围可交付 |

## 每次发布需要记录

demo原生/ROS编号、旧alias、执行器、配置revision及SHA、arm、工位与槽位、Epic配置、输入条件、完成状态、完整实机run_id、ROS result、跨机通信结果、打包manifest。

请求被接收、脚本退出和机械臂真实到位分别记录。中途失败返回已完成阶段、持物状态、当前位置和是否需要人工处理。取消完成以执行器确实停止的回读为依据。

## 首批适配顺序

- 保留 RAWU0-02 已交付Demo01和 RAWU0-01 原回center接口。
- 优先 RB2P5、RD1P0、RC0P0，已有明确完整原生成功。
- RD2P0先补当前V7参数归属；RC0F0、RA0F0提取持物结束出口。
- RA0P0补完整原生验证；其余五槽放置从下中能力派生。
- 专机抓取与六槽抓取补目标/进入/退出合同，再逐项验证。

底层控制算法和设备服务由现有backend持有，ROS客户端只提交业务任务并订阅反馈。
